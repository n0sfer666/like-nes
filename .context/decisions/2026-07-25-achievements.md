# ADR 0010: Достижения — детерминированное ядро-наблюдатель + плагинные бэкенды

- **Дата:** 2026-07-25
- **Статус:** **Accepted** (2026-07-25) — все 7 гейтов спеки #10 закрыты, проверка T4.
- **Контекст:** [спека #10](../specs/2026-07-25-achievements.md); опирается на
  [ADR 0006](2026-07-21-plugin-system.md) (ext-point + ABI-версия), [0003](2026-07-19-asset-pipeline.md)
  (zero-parse бандл), [0008](2026-07-23-build-deploy.md) (игра-образец, sim-golden),
  [0009](2026-07-25-licensing.md) (проприетарный SDK не вендорится).

## Проблема

Платформенные API достижений устроены принципиально иначе, чем ядро движка. Steam требует живого
клиента и отвечает асинхронно через колбэки; Google Play Games ходит в сеть; консольные SDK
добавляют ещё и сертификационные требования. Всё это — источники недетерминизма и отказов.

Движок при этом построен на противоположном свойстве: `fix32`-симуляция воспроизводима побитово,
replay из #4 и golden-хеш `0x32a094e89eacf2f2` из #8 — гейты, а не пожелания. Если условие
достижения вычислять внутри `sim::step()`, а анлок отправлять оттуда же, то поведение симуляции
начнёт зависеть от того, запущен ли Steam-клиент. Это ломает replay, netplay (#11, где детерминизм —
предпосылка) и сам смысл golden-гейта.

Вторая половина проблемы — авторинг. Достижения — данные (их правят дизайнеры, они локализуются,
их список должен совпадать с тем, что заведено в кабинете Steam), но часть кейсов процедурная
(достижение на каждый биом/босса, сгенерированный контент). Один-единственный путь авторинга
здесь одинаково плох в обе стороны.

## Решения

| Аспект | Выбор |
|---|---|
| Место в архитектуре | **Чистый наблюдатель.** Sim не знает о достижениях; трекер питается наблюдаемым состоянием игры **после** тика. Инвариант, а не соглашение: sim-golden обязан совпадать с плагином платформы и без него |
| Ядро | детерминированное: статы `u64`, битсет анлоков, пороги, очередь событий анлока. Хешируется целиком → golden-гейт |
| Граница синхронности | ядро синхронно и детерминировано; **доставка** в бэкенды — вне тика, асинхронна, с очередью и ретраями |
| Идентификатор | стабильный строковый `id` → `AchId` (fnv1a). Строка — контракт с платформой (в кабинете Steam заведён именно API Name), хеш — рантайм-ключ |
| Статы как сущность | отдельно от достижений: платформы хранят их независимо, а прогресс-достижение — производная от стата |
| Авторинг | **оба пути**: манифест печётся `assetc` в zero-parse таблицу бандла (#5) — основной; `define()` из C++ — процедурный. Конфликт `id` — **hard error**, не «последний победил» |
| Персистентность | локальный снимок = единственный источник истины прогресса; запись атомарна (temp + `rename` + fsync), валидация по версии и хешу |
| Платформенный шов | новая ext-point `EXT_ACHIEVEMENT_BACKEND` в плагинном API (#6) ⇒ **bump `PLUGIN_API_VERSION` 1 → 2** |
| Steam | отдельный опциональный плагин; SDK **не вендорится**, собирается только при заданном `STEAMWORKS_SDK_DIR`; в дереве — фейковый бэкенд, повторяющий контракт `ISteamUserStats` |
| Реконсиляция | union локального и платформенного состояния, конфликт всегда в пользу «разблокировано» |
| Отказ платформы | тихая деградация: локальные достижения работают, события копятся в очереди, игра не падает |

## Ключевой tradeoff — наблюдатель вместо участника

Соблазнительная альтернатива — сделать достижения частью симуляции: условия писались бы прямо в
игровых системах, состояние ехало бы в том же снапшоте, что и мир, и «бесплатно» получалось бы
replay достижений. Отказ от неё стоит некоторого дублирования: наблюдателю приходится заново
доставать из мира то, что системы уже знали (счёт, киллы, фазу), и условия вида «убить босса, не
получив урона» требуют явного стата, а не чтения приватного состояния системы.

Взамен получаем ровно то, ради чего движок вообще детерминирован: sim остаётся замкнутым.
Достижения нельзя случайно превратить в вход симуляции; отсутствие Steam не меняет ни одного бита
игрового состояния; netplay (#11) не обязан синхронизировать прогресс достижений между пирами;
replay старой записи не «переанлочивает» достижения задним числом. И ровно поэтому регресс-гейт по
sim-хешу здесь не формальность: если он покраснел — нарушена архитектура, а не арифметика.

Вторая цена — **bump ABI плагинов** 1 → 2 ради седьмой ext-point. Альтернатива (протащить бэкенд
достижений через существующий `EXT_UI_PANEL`/`EXT_ECS_SYSTEM` или через «универсальный сервис»)
дешевле на день и хуже навсегда: бэкенд достижений имеет собственный контракт с колбэками, и
маскировка его под чужую точку расширения превратила бы `Registry` в свалку. Плагинов в природе
пока ноль, ломать нечего — момент для бампа лучший из возможных.

## Условия финализации (validation gate) — выполнены

Proposed → **Accepted**: все 7 гейтов спеки #10 закрыты, из них ключевые:

1. **Golden логики анлока** — `achievements_test`: `hash=0xe728fef199e87fc9`, `events=4`,
   run-to-run байт-идентично.
2. **Крэш/рестарт** — `ach_crash_test`: 12/12 рестартов с валидным снимком, 4 убийства пришлись
   между temp и `rename`.
3. **Плагинный шов** — fake-бэкенд получает declare/unlock/set_stat/commit; оффлайн-очередь
   досылается; ABI поднят до 2, старый бинарник отбивается диагностикой.
4. **Регресс #8** — `ach_sim_test`: `0x32a094e89eacf2f2` одинаково bare / с наблюдателем /
   с загруженным плагином-бэкендом.

Инвариант «наблюдатель» подтверждён и структурно: ядро достижений не линкуется в `sim`, а игровой
код вызывает `observe()` **после** `step()`.

## Последствия

- `PLUGIN_API_VERSION` = 2; `ExtKind` расширяется до семи значений, `Registry::named_` — до семи
  слотов. Все существующие тестовые плагины пересобираются; версия ABI отбивает старые бинарники
  явной диагностикой, а не UB.
- Появляется **первое персистентное состояние игрока** в движке (до #10 сохранений не было вообще).
  Формат снимка становится совместимостной поверхностью: смена раскладки требует версии и миграции.
- Условия достижений обязаны выражаться через статы/события, а не через чтение приватного состояния
  игровых систем. Это ограничение авторинга — плата за инвариант «sim не знает о достижениях».
- Steamworks SDK остаётся вне репозитория ⇒ CI никогда не проверит настоящий Steam. Живой прогон —
  ручная процедура; риск расхождения мока с реальным API принимается осознанно и снижается тем, что
  мок повторяет сигнатуры `ISteamUserStats`, а не «удобный» интерфейс.
- Дубликат `id` — hard error и на bake, и в рантайме. Это сознательно шумно: молчаливое
  переопределение достижения ломает контракт с платформой, где список заведён отдельно.
- В ABI добавлен `declare(key)`: адаптер платформы не может спросить «что уже разблокировано на
  сервере», не зная списка ключей каталога. Побочный эффект — плагин видит весь каталог, включая
  `hidden`; для платформ это норма (список и так заведён в их кабинете).
- Реестр держит строки **внутри mmap-региона** бандла (zero-parse). Отсюда жёсткое правило времени
  жизни: источник (`BundleSource`) обязан пережить `Registry`, иначе строки висячие. В игре это
  обеспечено порядком полей `Achievements::Impl`. По той же причине загрузка манифеста атомарна
  (`Registry::Transaction`): отказ на N-й записи откатывает и первые N-1, иначе размапленный регион
  оставил бы висячие строки.
- Симметричное правило на плагинной стороне: `Delivery` закрывает сессию бэкенда (`commit`+`end`)
  и потому обязана быть закрыта (`shutdown()`, идемпотентно) **до** выгрузки плагина. Автоматически
  отозвать бэкенд при `unload` нельзя — `Registry` не знает своих потребителей; это цена C-ABI
  плагинов и она фиксируется контрактом, а не механизмом.
