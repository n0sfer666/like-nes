# Спецификация: Выбор языка + архитектура ядра движка

- **Дата:** 2026-07-18
- **Статус:** язык **C++ — Accepted**; архитектура — pending PoC (T4). См. [ADR 0001](../decisions/2026-07-18-language-and-core.md)
- **Спека:** #1 из ≥10 (roadmap в [`../README.md`](../README.md))

## Контекст

Первая и фундаментальная спека проекта like-nes (2D game engine). Определяет язык
ядра/геймплея и базовую архитектуру, от которых зависят все последующие спеки.
Драйвер выбора — столп №1 (оптимизация RAM/диск/CPU/GPU в архитектуре) и столп №7
(один язык логики, обусловленный оптимизацией). Оригинальный бриф:
[`../notes/original-brief.md`](../notes/original-brief.md). Desk-research:
`~/wiki/dev/like-nes/benchmark/`.

## Требования

### Функциональные
- Ядро и геймплей на одном языке — **C++**.
- Геймплей перегружается на лету (hot-reload shared-lib через C-ABI), state в host.
- ECS как модель данных (flecs, archetype); детерминированное исполнение систем.
- Рендер кроссплатформенный (Dawn / WebGPU): desktop сейчас, консоли через HAL позже.
- Ассеты грузятся из кастомного бинформата (mmap + стриминг).
- Бандлится управляемый C++-toolchain с кросс-таргетами (desktop→mobile).

### Нефункциональные (столп №1)
- **RAM:** арены/пулы + per-frame allocator; без скрытых heap-аллокаций в кадре.
- **Диск:** кастомный паков., готовый-к-загрузке формат; компрессия (zstd/basis).
- **CPU:** SoA cache-locality (archetype ECS); детерминированный параллелизм.
- **GPU:** Dawn/WebGPU; потолок эффектов — уровень Hollow Knight (детально — render-спека #2).
- **Детерминизм:** бит-в-бит воспроизводимость симуляции (fixed timestep + fixed-point).
- **Устойчивость:** крэш геймплея не роняет редактор (SEH/сигнал-изоляция на границе).
- **Safety:** нет borrow-checker → ASan/UBSan в CI + дисциплина владения обязательны.

## Архитектура

См. [`../architecture.md`](../architecture.md). Слои: Gameplay(shared-lib, stateless) →
Host/Engine core C++(владеет state, flecs ECS, планировщик, аллокаторы, стриминг) → HAL →
Backends(Dawn render + platform). Инварианты — там же.

## API / Интерфейсы

- **shared-lib ABI:** стабильная `extern "C"` граница host↔gameplay; экспорт систем как
  чистых функций над указателями на ECS-хранилища; изоляция крэшей (SEH/signals).
- **ECS API:** flecs-запросы; регистрация систем в граф зависимостей (планировщик выводит
  детерминированный параллельный порядок).
- **Fixed-point тип:** геймплейный числовой тип (Q-формат, int32/int64) — эргономика в
  открытых вопросах.
- **Asset API:** загрузка по mmap-хендлу; ленивый стриминг; асинхронная декомпрессия.

## Edge Cases

- Изменение схемы компонентов между reload-ами (stateless lib смягчает, но add/remove
  полей компонента требует стратегии миграции — открытый вопрос).
- Крэш/исключение внутри системы в середине параллельного тика (изоляция + откат тика).
- Расхождение fixed-point между x86 и ARM (не должно быть — это и проверяет T4).
- Мобильный/старый GPU не поддерживает фичу WebGPU (fallback / feature-detection).
- Долгая компиляция shared-lib блокирует итерацию (замерить, бюджет latency).
- mmap-ассет недоступен/повреждён (graceful error, не крэш).
- UB из-за ручного управления памятью (арены/unsafe) — ловится ASan/UBSan в CI.

## Риски и митигации

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Потеря memory safety (нет borrow-checker) → UB в аренах/unsafe | Высокая | ASan/UBSan в CI; дисциплина владения; проверки арен в debug |
| Fixed-point ломает эргономику геймплея | Средняя | Удобная fixed-math либа/тип как «геймплейное число» |
| Детерминизм незаметно ломается (параллелизм/float) | Высокая | Детерм. планировщик + fixed-point + T4 golden-hash x86↔ARM |
| Крэш-изоляция в C++ сложнее (нет catch_unwind) | Средняя | SEH на Windows / signal-хендлеры на *nix; PoC-проверка |
| Hot-reload shared-lib нестабилен (C-ABI/lifetime) | Средняя | Stateless lib + `extern "C"` граница + PoC-замер |
| WebGPU-потолок ниже нужного для сложных эффектов | Средняя | Проверить shader-spike; нативный Vulkan escape hatch через HAL; render-спека #2 |
| Долгий цикл компиляции убивает итерацию | Средняя | Замер в PoC; инкрементальная сборка; бюджет latency |

## Тестовая стратегия

- **Уровень: T4.** DoD = ADR + walking-skeleton PoC + регресс-тест детерминизма.
- **Walking-skeleton PoC:** окно → Dawn/WebGPU-треугольник → flecs ECS → fixed-point тик
  → детерм. планировщик → hot-reload shared-lib roundtrip. Запуск на **Steam-десктопе:
  Linux, macOS, Windows** (цель №1). Мобилки отложены (см. stack.md).
- **T4 golden-hash:** хеш состояния ECS после N тиков одинаков (a) между прогонами,
  (b) между **x86 (Linux/Windows) и ARM (macOS Apple Silicon)** — кросс-арх проверка
  детерминизма на десктоп-таргетах. Красный тест = сломан детерминизм.
- **Замеры:** hot-reload latency, пик RAM, время загрузки ассета, оверхед драйва Dawn.
- **CI:** ASan/UBSan прогоны (safety вместо borrow-checker).

## Открытые вопросы

1. Эргономика fixed-point: свой удобный fixed-type / математическая либа.
2. Точная граница HAL: что абстрагируем под консоли (только рендер, или аллокатор/FS/ввод/тайминг).
3. Стратегия миграции схемы компонентов при hot-reload (add/remove полей).
4. Целевой бюджет hot-reload latency (сколько секунд приемлемо).
5. Dawn vs wgpu-native: какой WebGPU-бэкенд брать (Dawn зрелее в C++; wgpu-native — C API).

> Закрыто: «знакомость языка» критерием НЕ является (язык — только под скорость игр).
> «Знакомость интерфейса» из брифа относится к IDE (спека #7: следовать привычным паттернам UX).
