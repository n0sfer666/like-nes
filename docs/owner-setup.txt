like-nes — прогон проверки на чистой машине
Шпаргалка для владельца. Подробности по гейтам — docs/owner-verification.md,
общая установка — docs/first-run.md.

Все команды ниже прогнаны на macOS: вывод, который в них обещан, — настоящий,
а не предполагаемый.

--- WINDOWS: короткий путь -----------------------------------------------

  Из ЛЮБОГО шелла (обычный PowerShell годится), в корне репозитория:

      scripts\win-dev.bat setup     поставить всё через winget
      scripts\win-dev.bat build     сконфигурировать и собрать
      scripts\win-dev.bat check     прогнать owner_check.sh
      scripts\win-dev.bat game      запустить игру

  Скрипт сам находит установку VS через vswhere и поднимает vcvars64 —
  правильный ярлык в меню Пуск искать больше не нужно. После setup шелл
  надо ОТКРЫТЬ ЗАНОВО: PATH меняется только для новых процессов.
  Ещё есть `shell` (отдаёт cmd с готовым x64-окружением) и `clean`
  (удаляет каталог build — он помнит компилятор).

  Единственное, чего winget не ставит: драйвер видеокарты от вендора
  (DX12). Обычно уже стоит.

--- WINDOWS: то же руками ------------------------------------------------

  1. Visual Studio Build Tools 2022+ — компилятор без IDE, ~5 ГБ против
     20+ у Community. Полная IDE ничего к сборке не добавляет.
     — workload "Desktop development with C++" (приносит cmake и ninja)
     — ПРОВЕРИТЬ во вкладке "Individual components", что отмечен
       "Windows 11 SDK" (10.0.2xxxx). Без него нет rc.exe и mt.exe,
       и сборка падает сообщением, которое про SDK молчит — см. раздел 6.
     https://visualstudio.microsoft.com/downloads/
  2. Git for Windows (нужен и сам git, и его bash)
     https://git-scm.com/download/win
  3. Python 3 с python.org (галочка "Add python.exe to PATH")
     ВАЖНО: python3 из Microsoft Store не годится — это заглушка,
     она открывает магазин и ничего не исполняет.

  Всё дальше — ТОЛЬКО из "x64 Native Tools Command Prompt for VS":
  в обычном cmd/PowerShell нет cl.exe, а в Git Bash нет окружения vcvars.
  Именно x64 Native, а не просто "Developer Command Prompt for VS" и не
  "Developer PowerShell": те по умолчанию дают 32-битный компилятор, а
  дерево 64-битное — конфигурирование остановится на этом с явной
  ошибкой. В меню Пуск ярлык лежит рядом, в папке Visual Studio 2022.
  Разрядность видно по путям: нужен bin\Hostx64\x64\cl.exe.

  Важно: 32-битный шелл — НЕ признак того, что чего-то не хватает.
  Компонент "MSVC — x64/x86 build tools" кладёт оба хоста сразу,
  доустанавливать нечего, вопрос только в том, какой ярлык открыт.

--- ARCH LINUX (чистая система) ------------------------------------------

  sudo pacman -S --needed base-devel cmake ninja git python \
      libx11 libxrandr libxinerama libxcursor libxi \
      vulkan-icd-loader vulkan-tools mesa

  Драйвер Vulkan под своё железо (один из):
      vulkan-radeon      # AMD
      vulkan-intel       # Intel
      nvidia-utils       # NVIDIA
      vulkan-swrast      # программный lavapipe, если железа/драйвера нет

  Звук (без него игра честно скажет "audio: off" и поедет дальше):
      sudo pacman -S --needed pipewire pipewire-pulse alsa-lib

  Только для нативного Wayland (гейт 6, вторая сессия):
      sudo pacman -S --needed wayland wayland-protocols libxkbcommon

--- FEDORA / NOBARA (чистая система) --------------------------------------

  Nobara — это Fedora с преднастроенными репозиториями и драйверами, так что
  всё ниже — обычные пакеты Fedora.

  sudo dnf install -y gcc-c++ cmake ninja-build git python3 \
      libX11-devel libXrandr-devel libXinerama-devel libXcursor-devel \
      libXi-devel libxkbcommon-devel mesa-libGL-devel \
      vulkan-loader vulkan-tools mesa-vulkan-drivers

  mesa-libGL-devel в списке не по ошибке: GL/gl.h тянет сам glfw3.h под X11,
  независимо от того, что мы рисуем не через OpenGL. На Debian заголовок
  приезжает зависимостью xorg-dev, поэтому в строке для Ubuntu его не видно.
  Без него сборка падает на зависимости glfw3webgpu:
      fatal error: GL/gl.h: No such file or directory

  mesa-vulkan-drivers несёт сразу radv (AMD), anv (Intel) и lavapipe
  (программный) — отдельный пакет под свою карту, как в Arch, ставить не
  надо. NVIDIA: на Nobara проприетарный драйвер уже стоит из коробки, на
  чистой Fedora — akmod-nvidia из RPM Fusion.

  Только для нативного Wayland (гейт 6, вторая сессия):
      sudo dnf install -y wayland-devel wayland-protocols-devel

  Звук: pipewire в Nobara/Fedora уже стоит и настроен, ставить нечего.

  ВАЖНО, специфика Nobara: систему обновлять СВОИМ обновлятором
  (`nobara-sync cli` или приложение "Update System"), а не `dnf upgrade` —
  Nobara подменяет часть пакетов Fedora своими, и обычный upgrade их
  откатывает. Установка отдельных пакетов через dnf (команды выше) —
  штатная, upgrade — нет.

  Если чего-то не хватило (список выше — то, что нужно нашему дереву,
  а GLFW со временем может попросить больше):
      sudo dnf install -y dnf-plugins-core
      sudo dnf builddep glfw     # ровно то, чем собирают GLFW в Fedora

2. СБОРКА И АВТОМАТИЧЕСКИЙ ПРОГОН
===========================================================================

  git clone https://github.com/n0sfer666/like-nes.git
  cd like-nes
  cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
  cmake --build build

Linux / macOS:
  bash scripts/owner_check.sh

Windows — короткий путь, из любого шелла:
  scripts\win-dev.bat build
  scripts\win-dev.bat check

Windows — руками, из x64 Native Tools Command Prompt:
  "C:\Program Files\Git\bin\bash.exe" scripts/owner_check.sh

Windows, ОДИН РАЗ НА МАШИНУ, до первого прогона — из PowerShell админом:

  Add-MpPreference -ExclusionPath 'C:\путь\к\like-nes'

Без этого защитник запрещает запуск свежесобранных неподписанных бинарей
("не удалось проверить подлинность издателя"), и тесты не проваливаются —
они не выполняются вовсе. В отчёте такие строки помечены BLOCKED и кодом
возврата (126 — запуск запрещён), а в итоге посчитаны отдельным числом
"не запущено". Строка BLOCKED означает, что про эту цель машина не сказала
ничего; строка FAIL — что цель отработала и разошлась.

Отчёт: build/owner-report-<os>.txt (Windows: build\owner-report-*.txt).
Прислать его целиком.

Windows: не открывать проект как папку в самой Visual Studio. Её CMake-
интеграция кладёт сборку в out\build\x64-Debug, а гейты ждут каталог build
в корне (иначе — BUILD_DIR=out\build\x64-Debug перед вызовом скрипта) и
конфигурацию Release. Командная строка выше — единственный проверенный путь.

3. РУЧНАЯ ПРОВЕРКА — ИГРА
===========================================================================

Дальше пути в стиле Linux/macOS. На Windows: слэши обратные, бинарь с .exe,
переменные через отдельный `set VAR=значение` перед запуском.

--- A. Просто поиграть ----------------------------------------------------

  ./build/game_sidescroller

  Стартовые строки должны быть примерно такие (это уже проверка — каждая
  говорит, что подсистема поднялась):

    [game] assets: baked bundle .../game.bundle (BC7 512x256)
    [game] audio: on (SFX + music)
    [game] achievements: 5 defined, 0 unlocked, backend: local
    [game] WASD/arrows/LStick = move · gamepad: <бэкенд> · Esc = quit

  Управление: WASD или стрелки — движение, пробел или ЛКМ — огонь,
  геймпад: левый стик — движение, южная кнопка (A/X) — огонь. Esc — выход.

  На что смотреть, играя 3–5 минут:
    - враги стреляют и умирают, счёт растёт, босс появляется;
    - звук: выстрелы, взрывы, музыка — без заикания и хрипа;
    - тост достижения выезжает после первого убитого врага (First Blood);
    - кадр не рвётся, картинка не мерцает;
    - Esc закрывает окно и печатает "[game] window clean exit"
      (не "крестиком" — крестик тоже должен работать, проверь оба).

  Если жалуется на ассеты — LIKENES_ASSETS=<путь к example_ugly_game/assets>.

--- B. Достижения переживают перезапуск -----------------------------------

  LIKENES_SAVE_DIR=./saves-probe ./build/game_sidescroller
     → поиграть до тоста First Blood, выйти
  LIKENES_SAVE_DIR=./saves-probe ./build/game_sidescroller
     → строка старта теперь говорит "N unlocked", N > 0

  Windows:
     set LIKENES_SAVE_DIR=%CD%\saves-probe
     build\game_sidescroller.exe

  В каталоге ./saves-probe должен лежать achievements.save.
  Каталог временный — после проверки удаляй.

--- C. Достижения без сети (опционально, но дёшево) -----------------------

  Фейковый бэкенд умеет притворяться, что сети нет первые N запусков
  подключения: прогресс копится локально и досылается позже.

  Linux/macOS:
    LIKENES_SAVE_DIR=./saves-probe \
    LIKENES_ACH_PLUGIN=build/plugin_ach_fake.so \
    ACH_FAKE_OFFLINE=2 ./build/game_sidescroller

  Windows:
    set LIKENES_ACH_PLUGIN=build\plugin_ach_fake.dll
    set ACH_FAKE_OFFLINE=2
    build\game_sidescroller.exe

  Строка старта должна сказать "backend: plugin", а игра — работать так же.

--- D. Офскрин-рендер: демо-режим -----------------------------------------

  ./build/game_sidescroller --demo ./demo-out --frames 300

  Окна не открывает, пишет frame_0000.png … frame_0299.png и печатает
  "[game] demo wrote 300 frames to ...". Открой пару кадров глазами:
  это путь рендера в текстуру, которого живая игра не показывает.

--- E. Звук на живом железе (в CI не существует) --------------------------

  Во время игры воткни/выдерни наушники, переключи устройство вывода в ОС.
  Ожидание: звук либо продолжается на новом устройстве, либо честно
  замолкает — но игра не падает и не зависает.

--- F. Бейк ассетов байт-в-байт -------------------------------------------

  ./build/assetc --game example_ugly_game/assets ./rebake.bundle

  Должен напечатать:
    [assetc] bundle_hash = 0xa67f56b681aed040

  Это тот же хеш, что на macOS. Отличается — значит бейк не детерминирован
  между ОС, и это находка (пришли строку целиком).

  Шаг остался ручным ТОЛЬКО из-за текстуры: она требует tint и basisu, а их
  нет ни на раннерах, ни на чистой машине. Секции, которые пекутся чистыми
  парсерами (input.txt, achievements.txt), с 2026-08-08 сверяются машинно и
  на трёх ОС:

    ./build/assetc --verify-game example_ugly_game/assets \
        example_ugly_game/assets/game.bundle

  Должен напечатать:
    [assetc] verify: PASS - 2 tool-free section(s) checked against ...

  Отдельно гонять не надо — это шаг CI и этап preflight. Здесь он назван,
  чтобы `bundle_hash` выше читался как проверка ИМЕННО текстурного бейка.

4. РУЧНАЯ ПРОВЕРКА — ГЕЙТЫ РАУНДОВ #13 и #14

--- G. Редактор, X11 и Wayland (гейт 6, только Linux) ---------------------

GLFW по умолчанию собран только под X11, под Wayland-сессией такой бинарь
работает клиентом XWayland — поэтому сборки две и сессии две.

  cmake -S . -B build-way -G Ninja -DCMAKE_BUILD_TYPE=Release -DLINUX_WAYLAND=ON
  cmake --build build-way --target editor_shell

  echo $XDG_SESSION_TYPE   # должно печатать x11
  ./build/editor_shell
  echo $XDG_SESSION_TYPE   # должно печатать wayland
  ./build-way/editor_shell

В каждой сессии: вьюпорт рисует, клик в Hierarchy выделяет объект, гизмо его
двигает, числа в Inspector едут следом, Undo возвращает назад.
Скриншот каждой сессии: gate6-x11.png, gate6-wayland.png.

Чёрный вьюпорт → vulkaninfo --summary | head: нет устройства — это драйвер,
а не редактор.

Nobara (и любая современная Fedora) логинит в Wayland по умолчанию, так что
х11-половина гейта требует отдельной сессии. Порядок:

  1. Выйти из сессии (не перезагрузка — logout).
  2. На экране входа выбрать сессию: в GNOME это шестерёнка рядом с кнопкой
     "Войти", в KDE — список слева внизу. Нужен пункт со словом X11.
  3. Залогиниться и проверить: echo $XDG_SESSION_TYPE → x11

  Пункта с X11 в списке нет — сессию надо доставить:
      GNOME:  sudo dnf install gnome-session-xsession
      KDE:    sudo dnf install plasma-workspace-x11
  Пакета нет в репозитории (в свежих Fedora сессию GNOME под X11 вырезали) —
  подойдёт ЛЮБОЙ X11-сеанс, гейт проверяет наш бинарь под X11, а не рабочий
  стол: sudo dnf install i3 (или openbox) даст пункт в списке сессий.

Отдельная ловушка Wayland-сборки: без wayland-protocols-devel конфигурирование
падает на поиске wayland-scanner ещё до компиляции — это не наша ошибка, а
недостающий пакет.

--- H. Правка кода → пересборка → изменение видно (гейт 8) ----------------

  1. ./build/editor_shell — убедиться, что рисует
  2. ./build/game_sidescroller — посмотреть на фон
  3. в example_ugly_game/draw.cpp заменить
       a.clearValue = WGPUColor{0.02, 0.02, 0.07, 1.0}
     на
       a.clearValue = WGPUColor{0.25, 0.02, 0.05, 1.0}
     (рендер-сторона: sim-хеш не двигается, а глазом видно)
  4. cmake --build build --target game_sidescroller
  5. ./build/game_sidescroller — фон стал тёмно-красным
  6. git checkout example_ugly_game/draw.cpp  ← вернуть обязательно

Числа "best / median" из раздела про цикл в отчёте owner_check — тоже часть
этого гейта, они нужны фактом для Linux и Windows.

--- I. Живой ввод: пад (гейт 8 спеки #14) ---------------------------------

  cmake --build build --target framework_input_probe
  ./build/framework_input_probe example_ugly_game/assets/input.txt

  1. Воткнуть пад НА ХОДУ → строка
     pad 0 CONNECTED vid=… pid=… name="…" -> profile '…'
     Профиль должен соответствовать устройству; 'generic' у неизвестной
     модели — это работающий фолбэк, а не провал.
  2. Стик → move=(…) едет, в покое ровно (+0.00,+0.00). Южная кнопка и
     пробел → fire:# у обоих.
  3. Клавиша 1 → перебинд 'fire' → нажать клавишу, уже занятую другим
     действием → probe откажет и назовёт владельца → F заберёт силой.
  4. S — сохранить, Esc — выйти, запустить снова: строка
     "overlay loaded … N edit(s)" (идёт сразу за "move axes resolved by
     name: …"). Потом X и S — вернуть чистый пресет.
  5. Выдернуть пад на ходу → "pad 0 DISCONNECTED -> ... 'generic'",
     клавиатура продолжает играть, ничего не залипает.
  6. ./build/game_sidescroller с падом — корабль летит по стику.

Linux, если пад не виден: sudo usermod -aG input $USER и перелогиниться.
Строка "input dev" в отчёте owner_check показывает, что увидел скрипт.

--- J. Цена шага физики (гейт 8 спеки #15) ---------------------------------

  cmake --build build --target framework_physics_perf_test
  ./build/framework_physics_perf_test

owner_check.sh гоняет это сам и кладёт вывод в отчёт — руками нужно, только
если смотришь отдельно. ОЖИДАЕМЫЙ вывод построчно; значений счётчиков тут
намеренно НЕТ — они закреплены константами внутри бинаря, а копия в runbook'е
не проверяется ничем и после первого же перепина просит подтвердить прошлогод-
ние числа:

    framework physics perf gate (500 bodies)
      heap: bodies=500 pairs=<n> broad=<n> narrow=<n> vel=<n> pos=<n>
      heap: worst=<время> ms mean=<время> ms allocs=0
      scatter: bodies=500 pairs=<n> broad=<n> narrow=<n> vel=<n> pos=<n>
      scatter: worst=<время> ms mean=<время> ms allocs=0
      column: bodies=0 pairs=0 broad=<n(n-1)/2> narrow=0 vel=0 pos=0
      column: worst=<время> ms mean=<время> ms allocs=0
    framework-physics-perf: PASS

  1. Сверять счётчики глазами не надо: разошедшееся число печатает свою
     строку "FAIL: <сцена>: <поле> = N, reference says M" и роняет прогон.
     Любая строка FAIL — находка серьёзнее любого времени: две ОС разошлись
     в арифметике, то есть тот же класс дефекта, что ловит голден состояния.
     Прислать вывод целиком. Замеренная таблица — в спеке
     .context/specs/2026-07-26-physics-core.md.
  2. Время различаться ОБЯЗАНО — его тут и меряют. Судить "heap: mean"
     против бюджета кадра 16.67 мс. Замерено на трёх машинах:
     M3 Pro 3.64 мс (22%), Nobara/gcc 8.583 мс (51%), Windows/MSVC на той
     же коробке 9.594 мс (58%).
     Эталон — САМАЯ МЕДЛЕННАЯ строка, а не самая быстрая: цифра с M3 Pro
     описывает M3 Pro, а не движок, и именно на ней выбраны 16 итераций
     решателя (было 8, кадр 2.25 мс). Матрицу снимает scripts/perf_sweep.sh,
     см. owner-verification.md; прогон 2026-08-13 закрыл вопрос об
     итерациях (16 остаются: на 300 телах восемь не дешевле, а дороже) и
     оставил открытым число тел — не мерена середина между 300 и 500:
     Linux/macOS:  bash scripts/perf_sweep.sh 16:400 16:350 8:300
     Windows — ДВА шага: git-bash сам по себе не видел vcvars64.bat, и
     cl.exe в нём не соберёт ничего (та же причина, по которой там и
     owner_check.sh зовётся через win-dev.bat):
       scripts\win-dev.bat shell
       "%ProgramFiles%\Git\bin\bash.exe" scripts/perf_sweep.sh 16:400 16:350 8:300
     Полный путь к bash.exe не педантизм: Git for Windows кладёт в PATH
     только свой cmd\, короткого bash там может не оказаться. Из голого
     git-bash скрипт остановится сам и назовёт эти две строки.
     Судить именно mean, а не worst: на трёх повторах одной ячейки среднее
     сошлось до 0.8%, а худшее разошлось на 20% при том же бинаре и той же
     сцене — худшее ловит чужой процесс, а не цену шага.
     Строку с пометкой ШУМ в колонке "контроль" читать нельзя: сцена column
     при равной работе стоила разного, значит машину грузило посторонним, и
     такую ячейку надо перезапустить. Прогон с ней возвращает код 2.
     Цифру с каждой машины прислать: она идёт в таблицу трёх машин в спеке.
  3. allocs=0 на всех трёх сценах.

  column с bodies=0 и нулями у решателя — ЭТО НОРМА, а не пустая сцена: её
  тела кинематические намеренно, решать там нечего. bodies=0 не значит "никто
  не двигается": шаг обходит все 500 и интеграцией, и клампом границ, а
  счётчик считает тела, к которым применены тяготение и затухание, то есть
  нагрузку на решатель. Сцена мерит ровно одно — вырождение широкой фазы в
  полный перебор, 124750 = 500*499/2.

6. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
===========================================================================

--- "The C compiler ... is not able to compile a simple test program" -----

Смотреть НЕ на первую строку, а на конец вывода. Если там

    --mt=CMAKE_MT-NOTFOUND
    RC Pass 1: command "rc /fo ..." failed ... no such file or directory

то компилятор ни при чём: rc.exe и mt.exe приносит Windows SDK, отдельный
компонент. Лечение:

  1. Visual Studio Installer → Modify → Individual components →
     отметить "Windows 11 SDK" → Modify.
  2. Удалить каталог сборки целиком (out\build\x64-Debug или build):
     в нём застрял кеш с CMAKE_MT-NOTFOUND, он переживёт установку SDK.
  3. В x64 Native Tools Command Prompt проверить: where rc и where mt
     должны печатать пути внутри C:\Program Files (x86)\Windows Kits\10\bin\
  4. Конфигурировать заново.

Строка "windows sdk :" в паспорте owner_check.sh показывает это же —
но она видна только после того, как сборка уже прошла, поэтому проверка
через where быстрее.

--- "like-nes собирается только под 64 бита" -----------------------------

Шелл 32-битный — доустанавливать в VS Installer нечего, x64-компилятор
уже лежит рядом (bin\Hostx64\x64\cl.exe). Самое короткое лечение:

    scripts\win-dev.bat clean
    scripts\win-dev.bat build

Дальше — то же самое руками. "Developer Command Prompt for VS" и "Developer PowerShell"
дают по умолчанию x86-тулчейн (в путях видно bin\Hostx86\x86\cl.exe), а
предсобранный wgpu-native всё равно подставляет x86_64-библиотеку. Лечение:
закрыть шелл, открыть "x64 Native Tools Command Prompt for VS", удалить
каталог build (кеш помнит компилятор) и сконфигурировать заново.

Если гейта не было и сборка дошла до кода — она падает по-другому:
capture.cpp даёт "C4244: преобразование uint64_t в size_t" под /W4 /WX.
Причина та же, наш код тут ни при чём.

--- "cl.exe not found" / CMake берёт не тот компилятор -------------------

Шелл запущен не из x64 Native Tools Command Prompt for VS. Обычный cmd,
PowerShell и Git Bash окружения vcvars не имеют.

--- Игра не находит ассеты -----------------------------------------------

  LIKENES_ASSETS=<путь к example_ugly_game/assets>
  (Windows: set LIKENES_ASSETS=...)

--- "fatal error: GL/gl.h: No such file or directory" (Fedora/Nobara) -----

Падает не наш код, а зависимость glfw3webgpu: заголовок тянет сам glfw3.h
под X11. На Debian он приезжает внутри xorg-dev, у Fedora метапакета нет.

  sudo dnf install -y mesa-libGL-devel

Переконфигурировать не нужно — повторить cmake --build build.

--- "Could not resolve host: github.com" при первом конфигурировании ------

Это DNS, а не дерево: первое конфигурирование качает зависимости. Часто
случается сразу после обновления системы, которое перезапустило резолвер.

  getent hosts github.com        должен напечатать IP
  resolvectl status | head -20   пусто → sudo systemctl restart systemd-resolved

Затем убрать stamp провалившейся загрузки и повторить конфигурирование
(каталог build целиком сносить не надо, скачанное останется):

  rm -rf build/_deps/<имя>-subbuild build/_deps/<имя>-src

--- Пад не виден на Linux ------------------------------------------------

  sudo usermod -aG input $USER   и перелогиниться.

Ещё вероятнее на игровом дистрибутиве: запущенный Steam со Steam Input
подменяет реальный пад виртуальным Xbox 360. На время гейта закрыть Steam.

--- Нет звука на Linux ---------------------------------------------------

Игра скажет "audio: off" и поедет дальше. Нужен pipewire/pipewire-pulse
(раздел 1). Проверить: pactl info
