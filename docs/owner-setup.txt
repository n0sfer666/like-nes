like-nes — прогон проверки на чистой машине
Шпаргалка для владельца. Подробности по гейтам — docs/owner-verification.md,
общая установка — docs/first-run.md.

Все команды ниже прогнаны на macOS: вывод, который в них обещан, — настоящий,
а не предполагаемый.

--- WINDOWS: короткий путь -----------------------------------------------

  Из ЛЮБОГО шелла (обычный PowerShell годится), в корне репозитория:

      scripts\win-dev.bat setup     поставить всё через winget
      scripts\win-dev.bat build     сконфигурировать и собрать
      scripts\win-dev.bat check     прогнать owner_check.sh
      scripts\win-dev.bat game      запустить игру

  Скрипт сам находит установку VS через vswhere и поднимает vcvars64 —
  правильный ярлык в меню Пуск искать больше не нужно. После setup шелл
  надо ОТКРЫТЬ ЗАНОВО: PATH меняется только для новых процессов.
  Ещё есть `shell` (отдаёт cmd с готовым x64-окружением) и `clean`
  (удаляет каталог build — он помнит компилятор).

  Единственное, чего winget не ставит: драйвер видеокарты от вендора
  (DX12). Обычно уже стоит.

--- WINDOWS: то же руками ------------------------------------------------

  1. Visual Studio Build Tools 2022+ — компилятор без IDE, ~5 ГБ против
     20+ у Community. Полная IDE ничего к сборке не добавляет.
     — workload "Desktop development with C++" (приносит cmake и ninja)
     — ПРОВЕРИТЬ во вкладке "Individual components", что отмечен
       "Windows 11 SDK" (10.0.2xxxx). Без него нет rc.exe и mt.exe,
       и сборка падает сообщением, которое про SDK молчит — см. раздел 6.
     https://visualstudio.microsoft.com/downloads/
  2. Git for Windows (нужен и сам git, и его bash)
     https://git-scm.com/download/win
  3. Python 3 с python.org (галочка "Add python.exe to PATH")
     ВАЖНО: python3 из Microsoft Store не годится — это заглушка,
     она открывает магазин и ничего не исполняет.

  Всё дальше — ТОЛЬКО из "x64 Native Tools Command Prompt for VS":
  в обычном cmd/PowerShell нет cl.exe, а в Git Bash нет окружения vcvars.
  Именно x64 Native, а не просто "Developer Command Prompt for VS" и не
  "Developer PowerShell": те по умолчанию дают 32-битный компилятор, а
  дерево 64-битное — конфигурирование остановится на этом с явной
  ошибкой. В меню Пуск ярлык лежит рядом, в папке Visual Studio 2022.
  Разрядность видно по путям: нужен bin\Hostx64\x64\cl.exe.

  Важно: 32-битный шелл — НЕ признак того, что чего-то не хватает.
  Компонент "MSVC — x64/x86 build tools" кладёт оба хоста сразу,
  доустанавливать нечего, вопрос только в том, какой ярлык открыт.

--- ARCH LINUX (чистая система) ------------------------------------------

  sudo pacman -S --needed base-devel cmake ninja git python \
      libx11 libxrandr libxinerama libxcursor libxi \
      vulkan-icd-loader vulkan-tools mesa

  Драйвер Vulkan под своё железо (один из):
      vulkan-radeon      # AMD
      vulkan-intel       # Intel
      nvidia-utils       # NVIDIA
      vulkan-swrast      # программный lavapipe, если железа/драйвера нет

  Звук (без него игра честно скажет "audio: off" и поедет дальше):
      sudo pacman -S --needed pipewire pipewire-pulse alsa-lib

  Только для нативного Wayland (гейт 6, вторая сессия):
      sudo pacman -S --needed wayland wayland-protocols libxkbcommon

--- FEDORA / NOBARA (чистая система) --------------------------------------

  Nobara — это Fedora с преднастроенными репозиториями и драйверами, так что
  всё ниже — обычные пакеты Fedora.

  sudo dnf install -y gcc-c++ cmake ninja-build git python3 \
      libX11-devel libXrandr-devel libXinerama-devel libXcursor-devel \
      libXi-devel libxkbcommon-devel mesa-libGL-devel \
      vulkan-loader vulkan-tools mesa-vulkan-drivers

  mesa-libGL-devel в списке не по ошибке: GL/gl.h тянет сам glfw3.h под X11,
  независимо от того, что мы рисуем не через OpenGL. На Debian заголовок
  приезжает зависимостью xorg-dev, поэтому в строке для Ubuntu его не видно.
  Без него сборка падает на зависимости glfw3webgpu:
      fatal error: GL/gl.h: No such file or directory

  mesa-vulkan-drivers несёт сразу radv (AMD), anv (Intel) и lavapipe
  (программный) — отдельный пакет под свою карту, как в Arch, ставить не
  надо. NVIDIA: на Nobara проприетарный драйвер уже стоит из коробки, на
  чистой Fedora — akmod-nvidia из RPM Fusion.

  Только для нативного Wayland (гейт 6, вторая сессия):
      sudo dnf install -y wayland-devel wayland-protocols-devel

  Звук: pipewire в Nobara/Fedora уже стоит и настроен, ставить нечего.

  ВАЖНО, специфика Nobara: систему обновлять СВОИМ обновлятором
  (`nobara-sync cli` или приложение "Update System"), а не `dnf upgrade` —
  Nobara подменяет часть пакетов Fedora своими, и обычный upgrade их
  откатывает. Установка отдельных пакетов через dnf (команды выше) —
  штатная, upgrade — нет.

  Если чего-то не хватило (список выше — то, что нужно нашему дереву,
  а GLFW со временем может попросить больше):
      sudo dnf install -y dnf-plugins-core
      sudo dnf builddep glfw     # ровно то, чем собирают GLFW в Fedora

2. СБОРКА И АВТОМАТИЧЕСКИЙ ПРОГОН
===========================================================================

  git clone https://github.com/n0sfer666/like-nes.git
  cd like-nes
  cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
  cmake --build build

Linux / macOS:
  bash scripts/owner_check.sh

Windows — короткий путь, из любого шелла:
  scripts\win-dev.bat build
  scripts\win-dev.bat check

Windows — руками, из x64 Native Tools Command Prompt:
  "C:\Program Files\Git\bin\bash.exe" scripts/owner_check.sh

Windows, ОДИН РАЗ НА МАШИНУ, до первого прогона — из PowerShell админом:

  Add-MpPreference -ExclusionPath 'C:\путь\к\like-nes'

Без этого защитник запрещает запуск свежесобранных неподписанных бинарей
("не удалось проверить подлинность издателя"), и тесты не проваливаются —
они не выполняются вовсе. В отчёте такие строки помечены BLOCKED и кодом
возврата (126 — запуск запрещён), а в итоге посчитаны отдельным числом
"не запущено". Строка BLOCKED означает, что про эту цель машина не сказала
ничего; строка FAIL — что цель отработала и разошлась.

Каталог УЖЕ исключён, а BLOCKED остались — причина вторая и другая:
Smart App Control (он же политика Device Guard). Проверить:

  Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy' |
    Select-Object VerifiedAndReputablePolicyState

0 — выключен, 1 — включён и блокирует, 2 — режим оценки. Он режет ЧАСТЬ
неподписанных сборок, а не все (на машине владельца determinism_test.exe
запускался, audio_golden.exe — нет, при той же сборке и тех же правах),
поэтому выглядит как плавающий гейт, а не как политика. Выключение:
Параметры -> Конфиденциальность и защита -> Безопасность Windows ->
Управление приложениями и браузером -> Smart App Control. Выключение
НЕОБРАТИМО: обратно только переустановкой Windows, поэтому решение ваше,
и ни один скрипт репозитория его не трогает.

Отчёт: build/owner-report-<os>.txt (Windows: build\owner-report-*.txt).
Прислать его целиком.

Windows: не открывать проект как папку в самой Visual Studio. Её CMake-
интеграция кладёт сборку в out\build\x64-Debug, а гейты ждут каталог build
в корне (иначе — BUILD_DIR=out\build\x64-Debug перед вызовом скрипта) и
конфигурацию Release. Командная строка выше — единственный проверенный путь.

===========================================================================
3. РУЧНАЯ ПРОВЕРКА — ИГРА
===========================================================================

Дальше пути в стиле Linux/macOS. На Windows: слэши обратные, бинарь с .exe,
переменные через отдельный `set VAR=значение` перед запуском.

--- A. Просто поиграть ----------------------------------------------------

  ./build/game_sidescroller

  Стартовые строки должны быть примерно такие (это уже проверка — каждая
  говорит, что подсистема поднялась):

    [game] assets: baked bundle .../game.bundle (BC7 512x256)
    [game] materials: on (3 pipeline(s), 0 fallback(s))
    [game] audio: on (SFX + music)
    [game] achievements: 5 defined, 0 unlocked, backend: local
    [game] WASD/arrows/LStick = move · gamepad: <бэкенд> · Esc = quit

  Размер в первой строке приезжает ИЗ БАНДЛА (секция `atlas_regions`), а не
  из кода: нарезка спрайтов после вертикали 3 спеки #17 читается по именам.
  Вместо неё может напечататься одна из двух строк отказа — обе означают, что
  игра пошла на процедурный атлас и картинка будет грубее:

    [game] assets: atlas_regions section unusable -> procedural
    [game] assets: bundle .../game.bundle unreadable -> procedural fallback

  Вторая строка — библиотека эффектов (спека #18): семь материалов делят три
  точки входа, поэтому пайплайнов три. `off` означает, что рядом с бинарём не
  нашёлся `library.bundle` — его кладёт тот же install-шаг, что и `game.bundle`,
  поэтому `off` после чистой сборки это находка, а не настройка руками. Ненулевые
  fallback'и означают, что материал назвал точку входа, которой в модуле нет:
  игра продолжает рисовать (в этом и смысл отката), а число — улика.

  Управление: WASD или стрелки — движение, пробел или ЛКМ — огонь,
  геймпад: левый стик — движение, южная кнопка (A/X) — огонь. Esc — выход.

  На что смотреть, играя 3–5 минут:
    - враги стреляют и умирают, счёт растёт, босс появляется;
    - звук: выстрелы, взрывы, музыка — без заикания и хрипа;
    - тост достижения выезжает после первого убитого врага (First Blood);
    - кадр не рвётся, картинка не мерцает;
    - Esc закрывает окно и печатает ДВЕ строки:
        [game] fx: peak <N> of 512, dropped 0
        [game] window clean exit
      dropped не 0 — находка: пул частиц переполнялся, искры переставали
      вылетать. peak — запас, в котором стоит этот ноль (скриптовый бой
      game_fx_test даёт 113, холостой полёт — 32).
      (не "крестиком" — крестик тоже должен работать, проверь оба).

  Если жалуется на ассеты — LIKENES_ASSETS=<путь к example_ugly_game/assets>.

--- B. Достижения переживают перезапуск -----------------------------------

  LIKENES_SAVE_DIR=./saves-probe ./build/game_sidescroller
     → поиграть до тоста First Blood, выйти
  LIKENES_SAVE_DIR=./saves-probe ./build/game_sidescroller
     → строка старта теперь говорит "N unlocked", N > 0

  Windows:
     set LIKENES_SAVE_DIR=%CD%\saves-probe
     build\game_sidescroller.exe

  В каталоге ./saves-probe должен лежать achievements.save.
  Каталог временный — после проверки удаляй.

--- C. Достижения без сети (опционально, но дёшево) -----------------------

  Фейковый бэкенд умеет притворяться, что сети нет первые N запусков
  подключения: прогресс копится локально и досылается позже.

  Linux/macOS:
    LIKENES_SAVE_DIR=./saves-probe \
    LIKENES_ACH_PLUGIN=build/plugin_ach_fake.so \
    ACH_FAKE_OFFLINE=2 ./build/game_sidescroller

  Windows:
    set LIKENES_ACH_PLUGIN=build\plugin_ach_fake.dll
    set ACH_FAKE_OFFLINE=2
    build\game_sidescroller.exe

  Строка старта должна сказать "backend: plugin", а игра — работать так же.

--- D. Офскрин-рендер: демо-режим -----------------------------------------

  ./build/game_sidescroller --demo ./demo-out --frames 300

  Окна не открывает, пишет frame_0000.png … frame_0299.png и печатает
  "[game] demo wrote 300 frames to ...". Открой пару кадров глазами:
  это путь рендера в текстуру, которого живая игра не показывает.

  Там же гоняется гейт 2 спеки #17 — эталонный кадр:

    ./build/game_sidescroller --frames 240 \
      --golden example_ugly_game/golden/scene_960x540.png --golden-selftest

  Должен напечатать три строки подряд:
    [game] golden control: PASS (blot, scatter and one-pixel shift refused)
    [game] golden repeat: ... PASS
    [game] golden frame: ... PASS

  Строка "frame" судит по "blob" — крупнейшему СВЯЗНОМУ пятну разошедшихся
  пикселей, а не по пику: на кромке спрайта растеризатор округляет пиксель
  на другую сторону контура, и канал там расходится на КОНТРАСТ кромки, а
  не на «немножко». Дефект двигает область, поэтому ловится пятном.

  Эталон испечён на Metal (M3 Pro), а у тебя настоящие драйверы AMD/NVIDIA/
  Intel — раннеры их не видят: там lavapipe (Linux) и DX12-WARP (Windows),
  оба программные. Поэтому именно твой прогон отвечает на вопрос, живёт ли
  выбранный допуск на ЖЕЛЕЗЕ, а не только между двумя софт-растеризаторами.
  Красный "golden frame" — не обязательно баг: пришли строку с числами
  целиком и файл golden_actual.png рядом с ним, по ним и решается, чинить
  рендер или расширять допуск. Перепекать эталон у себя (--update-golden)
  не надо: он пиннут на Metal осознанно.

--- E. Звук на живом железе (в CI не существует) --------------------------

  Во время игры воткни/выдерни наушники, переключи устройство вывода в ОС.
  Ожидание: звук либо продолжается на новом устройстве, либо честно
  замолкает — но игра не падает и не зависает.

--- F. Бейк ассетов байт-в-байт -------------------------------------------

  ./build/assetc --game example_ugly_game/assets ./rebake.bundle

  Должен напечатать:
    [assetc] bundle_hash = 0x1a557ae839e76ea0

  Это тот же хеш, что на macOS. Отличается — значит бейк не детерминирован
  между ОС, и это находка (пришли строку целиком).

  Шаг остался ручным ТОЛЬКО из-за текстуры: ей нужен basisu, которого нет ни
  на раннерах, ни на чистой машине. tint в команде тоже назван, но зовётся он
  лишь на шейдерах (engine/asset/codec.cpp), а их в наборе игры-образца нет:
  бейк проходит и без него. Секции, которые пекутся чистыми парсерами
  (input.txt, achievements.txt, movement.txt, tilemap.txt, atlas.txt), с 2026-08-08
  сверяются машинно и на трёх ОС:

    ./build/assetc --verify-game example_ugly_game/assets \
        example_ugly_game/assets/game.bundle

  Должен напечатать:
    [assetc] verify: PASS - 5 tool-free section(s) checked against ...

  Отдельно гонять не надо — это шаг CI и этап preflight. Здесь он назван,
  чтобы `bundle_hash` выше читался как проверка ИМЕННО текстурного бейка.

  Библиотека эффектов (спека #18) печётся отдельным бандлом и с 2026-09-03
  ВАЛИДИРУЕТСЯ на бэкендах машины, на которой идёт бейк. С 2026-09-03 тем же
  бандлом едет таблица светов (вертикаль 3) — именованным флагом, а не четвёртым
  путём: позиция, меняющая смысл, этот режим уже один раз подводила.

    ./build/assetc --materials engine/material/library/library.mat \
        engine/material/library/sprite_effects.wgsl /tmp/library.bundle \
        --lights engine/light/library/lights.txt

  Должен напечатать (Linux — Vulkan, Windows — D3D12, macOS — Metal;
  остальные два бэкенда называются пропущенными поимённо):
    [assetc] materials: <бэкенд> validated 7 material(s) in 3 pipeline(s)
    [assetc] materials: <бэкенд> skipped (no adapter on this machine)
    [assetc] materials: 1 of 3 target backend(s) checked
    [assetc] materials /tmp/library.bundle (6544 bytes, 3 assets)

  Три ассета, а не два: таблица материалов, текст модуля и таблица светов.
  Два — значит флаг `--lights` не доехал, и сверка бандла покраснеет байтами.

  «0 of 3 checked» на машине с рабочим GPU — находка: значит проверять было
  негде, а не что шейдер валиден. Отдельно гонять не надо, это этап `bundle`
  в preflight и шаг CI на трёх ОС; здесь он назван, чтобы строку было с чем
  сравнить, если preflight покраснеет.

  Горячая замена шейдера (гейт 3 спеки #18) проверяется двумя прогонами.
  Машинный — без окна и без глаз, возвращает код:

    cmake --build build --target material_hot_reload editor_shell
    ./build/material_hot_reload --work hot_reload_work
    LIKENES_MATERIAL_LIB=engine/material/library \
        ./build/editor_shell --gate3 gate3_work

  Должны напечатать (оба — код возврата 0):
    hot-reload: PASS
    gate 3: PASS (failures: 0)

  Строка `-> 6 pipeline(s) total` в выводе второго обязательна: три пайплайна
  до правки и три пересобранных после. `3` там значит, что не перезагрузилось
  ничего, а `rejected:` без `:строка:колонка:` — что диагностику панель
  показать может, а открыть по ней файл нет.

  Второй прогон — глазами, окном, и он же единственный отвечает на вопрос,
  ради которого фича написана. Процедура целиком (три правки в редакторе и
  две в живой игре, с ожидаемым поведением каждой) — §11
  docs/owner-verification.md.

  Свет как данные (гейт 7 спеки #18) — на машине с Metal голден, на прочих
  selftest:

    cmake --build build --target light_golden
    ./build/light_golden --golden engine/render/golden/lights_640x360.png

  Должно напечатать (код возврата 0):
    [gpu] <адаптер> | Metal | BC: yes
      lights: 5 source(s) in the table, 5 uploaded
      frame: 3 draw call(s) into the albedo target
      normals: 5 mapped from the table, 2 flat, 0 naming an unknown asset
      occluders: 4 mapped from the table, 3 open, 0 naming an unknown asset
      cost: <a> ms/frame without the pass, <b> ms/frame with it (30 frames each)
      golden engine/render/golden/lights_640x360.png: mean=0.00000 max=0.00000 frac=0.00000
    light-gpu: PASS

  Пять источников, а не три и не шесть: три было зашито в PoC-сцене, шесть
  влезало в прежний юниформ. Другое число значит, что кадр пришёл не из
  таблицы. Строка `normals` — про шаг B: карту спрайту выбирает ТЕКСТУРНЫЙ
  СЛОТ материала, пять материалов библиотеки его объявляют, два нет. Набор
  `7 mapped, 0 flat` или `0 mapped, 7 flat` значит, что проход привязал одну
  карту всем. Строка `occluders` — про шаг C, перекрывателей у слота
  `occlusion` четыре против пяти нормалей: наборы РАЗОШЛИСЬ намеренно, и
  совпади они, проход, читающий чужое имя слота, нашёл бы карты и дал бы кадр
  молча. Строка `cost` — замер, а не порог: на эталонной машине оба числа
  около 1.7 мс на кадр 640x360, и разница между ними — цена двух
  дополнительных проходов, каждый из которых рисует сцену повторно: в буфер
  нормалей и в буфер перекрытия.

  На Linux и Windows вместо голдена:

    ./build/light_golden --selftest

  Картинку смотреть глазами — §12 docs/owner-verification.md: восемь вопросов

--- G. Редактор, X11 и Wayland (гейт 6, только Linux) ---------------------

GLFW по умолчанию собран только под X11, под Wayland-сессией такой бинарь
работает клиентом XWayland — поэтому сборки две и сессии две.

  cmake -S . -B build-way -G Ninja -DCMAKE_BUILD_TYPE=Release -DLINUX_WAYLAND=ON
  cmake --build build-way --target editor_shell

  echo $XDG_SESSION_TYPE   # должно печатать x11
  ./build/editor_shell
  echo $XDG_SESSION_TYPE   # должно печатать wayland
  ./build-way/editor_shell

В каждой сессии: вьюпорт рисует, клик в Hierarchy выделяет объект, гизмо его
двигает, числа в Inspector едут следом, Undo возвращает назад.
Скриншот каждой сессии: gate6-x11.png, gate6-wayland.png.

Чёрный вьюпорт → vulkaninfo --summary | head: нет устройства — это драйвер,
а не редактор.

Nobara (и любая современная Fedora) логинит в Wayland по умолчанию, так что
х11-половина гейта требует отдельной сессии. Порядок:

  1. Выйти из сессии (не перезагрузка — logout).
  2. На экране входа выбрать сессию: в GNOME это шестерёнка рядом с кнопкой
     "Войти", в KDE — список слева внизу. Нужен пункт со словом X11.
  3. Залогиниться и проверить: echo $XDG_SESSION_TYPE → x11

  Пункта с X11 в списке нет — сессию надо доставить:
      GNOME:  sudo dnf install gnome-session-xsession
      KDE:    sudo dnf install plasma-workspace-x11
  Пакета нет в репозитории (в свежих Fedora сессию GNOME под X11 вырезали) —
  подойдёт ЛЮБОЙ X11-сеанс, гейт проверяет наш бинарь под X11, а не рабочий
  стол: sudo dnf install i3 (или openbox) даст пункт в списке сессий.

Отдельная ловушка Wayland-сборки: без wayland-protocols-devel конфигурирование
падает на поиске wayland-scanner ещё до компиляции — это не наша ошибка, а
недостающий пакет.

--- I. Живой ввод: пад (гейт 8 спеки #14) ---------------------------------

--- J. Цена шага физики (гейт 8 спеки #15) ---------------------------------

  cmake --build build --target framework_physics_perf_test
  ./build/framework_physics_perf_test

owner_check.sh гоняет это сам и кладёт вывод в отчёт — руками нужно, только
если смотришь отдельно. ОЖИДАЕМЫЙ вывод построчно; значений счётчиков тут
намеренно НЕТ — они закреплены константами внутри бинаря, а копия в runbook'е
не проверяется ничем и после первого же перепина просит подтвердить прошлогод-
ние числа:

    framework physics perf gate (350 bodies)
      heap: bodies=350 pairs=<n> broad=<n> narrow=<n> vel=<n> pos=<n>
      heap: worst=<время> ms mean=<время> ms allocs=0
      scatter: bodies=350 pairs=<n> broad=<n> narrow=<n> vel=<n> pos=<n>
      scatter: worst=<время> ms mean=<время> ms allocs=0
      column: bodies=0 pairs=0 broad=<n(n-1)/2> narrow=0 vel=0 pos=0
      column: worst=<время> ms mean=<время> ms allocs=0
    framework-physics-perf: PASS

  1. Сверять счётчики глазами не надо: разошедшееся число печатает свою
     строку "FAIL: <сцена>: <поле> = N, reference says M" и роняет прогон.
     Любая строка FAIL — находка серьёзнее любого времени: две ОС разошлись
     в арифметике, то есть тот же класс дефекта, что ловит голден состояния.
     Прислать вывод целиком. Замеренная таблица — в спеке
     .context/specs/2026-07-26-physics-core.md.
  2. Время различаться ОБЯЗАНО — его тут и меряют. Судить "heap: mean"
     против бюджета кадра 16.67 мс. На заявленных 350 телах прогон
     2026-08-22 дал 3.560 мс (21.4%) на Windows/MSVC и 2.931 мс (17.6%) на
     Nobara/gcc. Числа ниже — прежняя сцена на 500 телах, оставлены потому,
     что из них выросло правило судить по среднему: M3 Pro 3.64 мс (22%),
     Nobara/gcc 8.583 мс (51%), Windows/MSVC на той же коробке 9.594 (58%).
     Эталон — САМАЯ МЕДЛЕННАЯ строка, а не самая быстрая: цифра с M3 Pro
     описывает M3 Pro, а не движок, и именно на ней выбраны 16 итераций
     решателя (было 8, кадр 2.25 мс). Матрицу снимает scripts/perf_sweep.sh,
     см. owner-verification.md. Оба открытых числа закрыты: итерации —
     прогоном 2026-08-13 (16 остаются: на 300 телах восемь не дешевле, а
     дороже), тела — прогоном 2026-08-22 (350: столько же, сколько стоят
     восемь итераций при 400 телах, но с сохранённой глубиной стопки).
     Матрица ниже — процедура на будущее: её гоняют, когда цена шага
     меняется или появляется новая машина, а не каждый раунд.

     ИНСТРУКЦИЯ 1 — LINUX (и macOS). Три команды, из корня репозитория:

       git pull --ff-only
       cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
       bash scripts/perf_sweep.sh 16:400 8:400 16:350 8:300

     ИНСТРУКЦИЯ 2 — WINDOWS. Четыре команды: первые две из ЛЮБОГО шелла,
     последние две — из окна, которое откроет win-dev.bat:

       git pull --ff-only
       scripts\win-dev.bat shell
       cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
       "%ProgramFiles%\Git\bin\bash.exe" scripts/perf_sweep.sh 16:400 8:400 16:350 8:300

     Шаг win-dev.bat отдельный потому, что git-bash сам по себе не видит
     vcvars64.bat, и cl.exe в нём не соберёт ничего (та же причина, по
     которой там и owner_check.sh зовётся через win-dev.bat). Полный путь к
     bash.exe не педантизм: Git for Windows кладёт в PATH только свой cmd\,
     короткого bash там может не оказаться. Из голого git-bash скрипт
     остановится сам и назовёт эти две строки.

     Матрица из четырёх ячеек, а не трёх: 8:400 добавлена затем, чтобы у
     обоих сравнений был парный контроль. Без неё 400 тел меряются только
     на 16 итерациях, восемь — только на 300, и любая разница читается
     сразу и как «тела», и как «итерации».

     git pull --ff-only и -DCMAKE_BUILD_TYPE=Release стоят в инструкции не
     для порядка: это два потерянных прогона, 2026-08-22 и 2026-08-13. Оба
     промаха теперь отбиваются ДО первой пересборки, пока минуты не
     потрачены, — прогон печатает одно из двух и выходит:

       perf-sweep: checkout отстал от origin/dev на N коммит(ов) — замер
                   пошёл бы СТАРЫМ скриптом.
       perf-sweep: каталог 'build' собран как «Debug» (генератор ...), а не
                   Release.

     Второй отказ важнее, чем кажется. Debug-числа медленнее в разы, но ВСЕ
     контроли остаются зелёными: ячейки замедляются вместе, отношения между
     ними сохраняются, column совпадает, разброс мал. Такую таблицу нечем
     отличить от честной, кроме этой проверки.

     Первой строкой прогон печатает, ЧЕМ мерено, и повторяет это вплотную к
     таблице — чтобы версия уехала в чат вместе с куском вывода:

       perf-sweep: инструмент <sha> от <дата>, ячеек 4, повторов 3

     Приписка "дерево ГРЯЗНОЕ" в этой строке — не ошибка прогона, но таблица
     снята не тем, что лежит в origin: прислать её можно, закреплять по ней
     числа нельзя.
     Судить именно медиану, а не worst: на трёх повторах одной ячейки
     среднее сошлось до 0.8%, а худшее разошлось на 20% при том же бинаре
     и той же сцене — худшее ловит чужой процесс, а не цену шага. Ячейка
     меряется REPEATS раз (по умолчанию 3) БЕЗ пересборки между повторами,
     судейское число — их медиана, разброс (макс-мин)/медиана печатается
     своей колонкой: она и есть прямой ответ на "можно ли верить строке".
     Колонок в таблице девять: итераций тел медиана %бюдж худшее %бюдж
     разброс vel метка.
     Пометка ШУМ в колонке "метка" — разброс повторов от 5% ЛИБО сцена
     column при равной работе стоила разного (порог 10% и не меньше 100 мкс
     кадра). Прогон при этом НЕ красный, код 0: непереносим только абсолют
     такой строки, отношения к соседним строкам того же прогона годны.
     Нужен абсолют — перезапустить эту строку одну. Метка "?" значит "не
     проверено" (один повтор либо одна ячейка в группе), а не "чисто".
     Цифру с каждой машины прислать: она идёт в таблицу трёх машин в спеке.
  3. allocs=0 на всех трёх сценах.

  column с bodies=0 и нулями у решателя — ЭТО НОРМА, а не пустая сцена: её
  тела кинематические намеренно, решать там нечего. bodies=0 не значит "никто
  не двигается": шаг обходит все 350 и интеграцией, и клампом границ, а
  счётчик считает тела, к которым применены тяготение и затухание, то есть
  нагрузку на решатель. Сцена мерит ровно одно — вырождение широкой фазы в
  полный перебор, 61075 = 350*349/2 (было 124750 при 500 телах — счёт съехал
  вместе с заявленным числом тел 2026-08-22, и бинарь печатает новое).

--- K. Образец-платформер: живой прогон (гейт 8 спеки #16) ----------------

  Цель за IDE_POC, в наборе CI её нет — конфигурировать полным набором опций:

    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
    cmake --build build --target game_platformer
    ./build/game_platformer

  Windows: из x64 Native Tools prompt, затем
    build\game_platformer.exe

  Окно 960x720, вид внутри 320x240 при скейле x3. Уровень 640x240 — ШИРЕ
  вида намеренно: камера, которой некуда ехать, не проверяет свой кламп.
  Рисунка нет вовсе, только плоские квады: серо-синий — сплошной тайл,
  зелёный — склон, янтарный — односторонняя площадка, голубой — движущаяся
  платформа, красный — герой.

  Стартовая строка ровно одна:

    [platformer] WASD/arrows = move | space/up = jump | down+jump = drop | gamepad: <бэкенд> | Esc = quit

  <бэкенд> — "GameController.framework (macOS)", "evdev (Linux)",
  "XInput (Windows)" либо "none". Esc или крестик:

    [platformer] window clean exit

  Любая строка в stderr — находка, а не шум:
    "level unreadable"      — бандл рядом с бинарём устарел;
    "controls unavailable"  — из секции input пропало действие jump;
    "surface texture status <n> - frame skipped" каждый кадр — поверхность
                              не восстановилась после ресайза или смены
                              монитора.

  Пройти уровень слева направо и ответить на СЕМЬ вопросов. Первые шесть —
  те приёмы, что гоняет скриптованный прогон, и в этом суть: хеш говорит, что
  на трёх машинах они вышли ОДИНАКОВЫМИ, и ничего не говорит о том, приятен
  ли хоть один из них. Седьмой добавлен 2026-09-01: его скриптованный прогон
  НЕ делал, и живой прогон нашёл там три дефекта, мимо которых хеш ходил
  месяц.

    1. Бег и остановка: трогается и встаёт, когда просишь, или проезжает
       мимо точки, где отпустил?
    2. Прыжок: с удержанием выше, чем с касания — разница пригодна? Прыжок
       выходит, если нажать чуть РАНЬШЕ приземления (буфер) и чуть ПОЗЖЕ
       схода с края (койот)? Окна пинятся тестами в тиках; числа в них —
       нет.
    3. Склон: подняться, спуститься, встать на нём. На спуске держится
       поверхности или через тайл отрывается и дёргается?
    4. Односторонние: две янтарные плиты нарочно перекрываются по X.
       Пройти сквозь нижнюю СНИЗУ и встать сверху, потом вниз+прыжок —
       упасть обратно. Спуск случается с первого нажатия? Не ловит ли
       обратно ту площадку, которую велели покинуть?
    5. Движущаяся платформа: встать на голубую и не нажимать ничего —
       должна везти. Сойти с неё — отдаёт твою же скорость, а не швыряет?
    6. Стены и потолок: упереться в правую стену и в козырёк над карманом.
       Встаёт чисто или дрожит, липнет, ползёт вверх по грани?
    7. Края уровня и БОК платформы: уйти в левый край карты и попрыгать там —
       герой обязан остаться на уровне. Потом встать в воздухе на пути
       голубой плиты и дождаться её: она толкает перед собой, а не глотает.

  Пад подключён — пункты 1–3 повторить на стике. Мёртвая зона круговая
  (0.18) и общая на пару осей, поэтому диагональ — первое место, где
  вылезет неверная форма: диагональ, читающаяся как "спуститься сквозь
  площадку", это знак move_y, а не вкусовщина.

  ЗАПИСАТЬ ЭКРАН (спека просит запись прямо): macOS Cmd+Shift+5, GNOME
  Ctrl+Alt+Shift+R, Windows Win+G. Один проход уровня, тридцати секунд
  хватит.

  ПОД WAYLAND БРАТЬ ИМЕННО ВСТРОЕННУЮ ЗАПИСЬ. Проверено 2026-08-29 на
  Nobara 44 (GNOME, сессия wayland, окно через XWayland): "ffmpeg -f x11grab"
  снимает ЧЁРНЫЙ ролик — корень XWayland не несёт композита, и файл при этом
  пишется нормального вида, то есть пустая улика неотличима от полной, пока

  (id даёт "wmctrl -l") и содержимое в нём настоящее.

--- L. Цена тика персонажа (гейт 7 спеки #16) ------------------------------

  cmake --build build --target framework_character_perf_test
  ./build/framework_character_perf_test

owner_check.sh гоняет это вместе с пунктом J одним этапом (scripts/owner_perf.sh)
и кладёт вывод в отчёт — руками нужно, только если смотришь отдельно. Windows:
build\framework_character_perf_test.exe из того же prompt.

  Гейт прогоняет ОДИН И ТОТ ЖЕ записанный маршрут по двум картам — 256x32 и
  1024x256, ровно в 32 раза больше по площади. Счётчики обязаны совпасть
  ПОБИТОВО: инвариант 4 ("цена запроса не зависит от размера уровня") виден
  только сравнением, абсолютное число тайлов про него не говорит ничего.
  Значений счётчиков тут намеренно НЕТ по той же причине, что в пункте J.

    framework character perf gate (a target-size level costs a small one's tick)
      small:  map=256x32 (8192 tiles) queries=<n> scanned=<n>
      small:  worst tick = <n> queries / <n> tiles, hash=<хеш>
      small:  worst=<время> ms mean=<время> ms allocs=0 cols=[<lo>, <hi>]
      small:  ground=<n> air=<n> ceiling=<n> slope=<n>
      target: map=1024x256 (262144 tiles) queries=<n> scanned=<n>
      target: worst tick = <n> queries / <n> tiles, hash=<хеш>
      target: worst=<время> ms mean=<время> ms allocs=0 cols=[<lo>, <hi>]
      target: ground=<n> air=<n> ceiling=<n> slope=<n>
    framework-character-perf: PASS

  1. Любая строка FAIL — находка серьёзнее любого времени, как в пункте J.
  2. Строки счётчиков у small и target обязаны быть ОДИНАКОВЫМИ: queries,
     scanned, худший тик и хеш. Расходиться вправе только worst/mean — они
     про часы этой машины, а не про карту.
  3. "target: mean" СКЛАДЫВАЕТСЯ с "heap: mean" из пункта J: в настоящем
     кадре работают оба. Тик персонажа — маленькое слагаемое (M3 Pro
     2026-08-30: worst 0.087 мс, mean 0.0103 — 0.06% кадра; Nobara на Intel
     UHD 620, 2026-09-01: worst 0.2600, mean 0.0242 — 1.56% и 0.15%), и
     машина, где он дорастает до миллисекунды, и есть находка.
  4. allocs=0 на обеих картах.
  5. МЕРИТЬ НА НЕЗАНЯТОЙ МАШИНЕ. 2026-09-01 тот же бинарь на той же коробке
     дал worst=3.7349 мс (22% кадра) при трёх сборках рядом и 0.19-0.28 мс
     на тихой — разница в четырнадцать раз. Различить их по выводу НЕЛЬЗЯ:
     счётчики, худший тик и хеш закреплены в бинаре и печатаются одинаково,
     так что загруженный прогон выдаёт PASS и время, читающееся как находка
     о тике. Закрыть сборки в соседних окнах и мерить.

  ceiling в десятках против ground в сотнях — ЭТО НОРМА, а не тощий маршрут:
  карниз в шаблоне один, и маршрут проходит под ним несколько раз за круг.
  Все четыре счётчика (земля, воздух, потолок, склон) утверждаются ненулевыми
  намеренно: маршрут, переставший касаться склона или потолка, продолжал бы
  мерить уровень полегче и печатать PASS.

--- M. Цена кадра сети (гейт 8 спеки #22) ----------------------------------

  cmake --build build --target game_platformer_net_test
  bash scripts/owner_net_budget.sh

owner_check.sh гоняет это отдельным этапом сразу после пунктов J и L и кладёт
вывод в отчёт. Windows: то же самое из git-bash после scripts\win-dev.bat check.

  Третий замер кадра, и первый, внутри которого живёт ОТКАТ. Пункты J и L
  мерят шаг физики и тик персонажа; здесь мерится кадр сетевого пира целиком:
  шаг симуляции с откатами и записью .replay — и, ОТДЕЛЬНОЙ цифрой, чего
  стоит рядом сокет. Одно число вместо двух говорило бы, что кадр дорогой, но
  не что его съело, а лечатся половины в разных файлах.

  Мерит ТОТ ЖЕ бинарь, что ведёт запись: --peer пишет .replay строкой за тик.
  Пиры поднимаются напрямую, а не прогоном game_platformer_net_test: тот
  отдаёт stdout детей в /dev/null, и обе цифры до отчёта не доезжают.

    --- Цена кадра сетевого прогона (game_platformer_net_test --peer, гейт 8 спеки #22)
      peer send: ticks=417 rollbacks=<n> replayed=<n> forced=0 resent=<n>
      peer send: sim worst=<время> ms mean=<время> ms over 417 ticks
      peer send: net worst=<время> ms mean=<время> ms over <n> passes
      peer recv: ticks=417 rollbacks=<n> replayed=<n> forced=0 resent=<n>
      peer recv: sim worst=<время> ms mean=<время> ms over 417 ticks
      peer recv: net worst=<время> ms mean=<время> ms over <n> passes
      худший кадр пира recv: <время> мс из 16.67 (<n>% бюджета)
      худший кадр пира send: <время> мс из 16.67 (<n>% бюджета)

  1. Ненулевой выход — раньше любого времени. Строка "FAIL: пиры вышли
     ненулём" значит, что прогон не дошёл до конца; код 9 там — это "замер
     кадра не сошёлся с прогоном", то есть проба не сработала, и напечатанное
     рядом время описывает не быстрый кадр, а несработавшую пробу.
  2. "over 417 ticks" у обоих пиров: один замер на тик — арифметика, на
     которой стоит весь пункт.
  3. Две строки "худший кадр" — против 16.67 мс, и к ним ПРИБАВЛЯЮТСЯ
     "heap: mean" из J и "target: mean" из L: в настоящем кадре работает всё.
     M3 Pro 2026-09-03: recv 0.323 мс (1.9% кадра), send 0.212 мс (1.3%).
  4. recv дороже send — так и должно быть: откатывается именно получатель, он
     узнаёт ввод поздно, и проходов по сокету у него вдвое больше. Обратный
     порядок на твоей машине — находка.
  5. МЕРИТЬ НА НЕЗАНЯТОЙ МАШИНЕ, ровно по причине из пункта L: загруженный
     прогон печатает то же самое, только медленнее.

--- N. Живая сессия (гейт 9 спеки #22) — ПОЛОВИНА ЗАПУСКАЕТСЯ --------------

  Единственный пункт, которому нужны ДВЕ машины в одной сети — любая пара из
  Linux, Windows и macOS, разные лучше одинаковых. Обе собраны с ОДНОГО
  коммита: всё утверждение пункта в том, что из одного ввода выходит одно
  состояние, и два разных коммита отвечали бы на вопрос, которого никто не
  задавал. Сверить git rev-parse HEAD на обеих.

  До 2026-09-04 пункт не запускался вовсе: пиры адресовали петлю константой и
  знакомились через файл <prefix>-send.port на ОДНОЙ файловой системе. Теперь
  сосед называется аргументом, и сходимость проверяется по проводу. Вторая
  половина — «ощущается ли это одной игрой» — по-прежнему не спрашивается: пир
  headless по инварианту 2 спеки, смотреть не на что. Это долг движка, не твой.

  Адрес машины: ip addr (Linux), ipconfig (Windows), ipconfig getifaddr en0
  (macOS). Пропустить UDP через фаервол на ОБОИХ портах: каждая машина слушает
  свой и шлёт на чужой, то есть 7777 открыт на A, а 7778 — на B. Windows
  спросит сам на первом прогоне, Linux может потребовать sudo ufw allow
  7777/udp на A и sudo ufw allow 7778/udp на B.
  СНАЧАЛА померить провод, потому что итог пункта читается против него:

  ping -c 20 <вторая машина>

  Сборка на обеих:

  cmake --build build --target game_platformer_net_direct_test

  Машина A владеет вводом (у образца один герой, играет его одна сторона):

  ./build/game_platformer_net_direct_test --peer send \
    example_ugly_game/assets/game.bundle live --listen 7777 --at <B>:7778

  Машина B переигрывает приехавшее:

  ./build/game_platformer_net_direct_test --peer recv \
    example_ugly_game/assets/game.bundle live --listen 7778 --at <A>:7777

  Windows: то же самое из git-bash после scripts\win-dev.bat, бинарь
  build\game_platformer_net_direct_test.exe. Запускать B первой (она ждёт, A
  говорит первой) и обе в пределах двадцати секунд друг от друга:
  PEER_DEADLINE_MS равен 20 с, и пир, не услышавший соседа, выходит кодом 4, а
  не висит. Оба адреса называются с ОБЕИХ сторон намеренно: пир, выучивающий
  соседа из первой датаграммы, отдал бы своё окно подтверждений тому, кто
  успел первым, — на порту, который ради не-петли открыт на всех интерфейсах.

  Каждая сторона печатает три строки и кладёт рядом с собой .replay:

      peer send: ticks=417 rollbacks=<n> replayed=<n> forced=0 resent=<n> aliens=0
      peer send: sim worst=<время> ms mean=<время> ms over 417 ticks
      peer send: net worst=<время> ms mean=<время> ms over <n> passes

  Последнее поле, aliens=, печатается только этим прогоном и считает
  датаграммы, приехавшие НЕ с адреса, названного в --at, и отброшенные за
  это. На петле там всегда 0; на машине с несколькими интерфейсами (VPN,
  docker0, две карты) — не обязательно: сосед вправе ответить не с того
  адреса, который ты набрал. Пара, умершая на дедлайне с растущим aliens, —
  это маршрутизация, а пара с aliens=0 не услышала вообще ничего.

  1. Обе стороны вышли нулём и напечатали ticks=417. Ненулевой код — это
     ответ, а не помеха, и перед выходом пир печатает строку с причиной:
       2 — уровень не загрузился: путь к бандлу считается от ТЕКУЩЕГО
           каталога, поэтому запускать обоих из корня репозитория или писать
           путь целиком;
       3 — сосед не назван: опечатка в --at, задана половина пары аргументов
           или слово, которого разбор не понял (он его печатает);
       4 — дедлайн прошёл, соседа не слышно: в девяти случаях из десяти это
           фаервол, а при растущем aliens — маршрутизация (см. выше);
       5 — не записан файл результата: смотреть каталог, куда указывает
           префикс;
       6 — сокет непригоден: либо порт из --listen уже занят (строка скажет
           port N did not open), либо сокет отказал по ходу прогона;
       7 — не записана запись прогона, тот же вопрос к каталогу, что и у 5;
       9 — кадр не померен: это находка движка, прислать.
  2. Две записи — один файл, байт в байт. Это и есть гейт: sha256sum
     live-send.replay (Linux), shasum -a 256 (macOS), certutil -hashfile
     live-send.replay SHA256 (Windows). Сверять live-send.replay машины A с
     live-recv.replay машины B. Разойтись они вправе только при ненулевом
     forced — см. пункт 3.
  3. forced= на обеих сторонах. Ноль значит, что ввод каждого тика доехал и
     откат на нём сошёлся. Ненулевое — пир перестал ждать ввод, сыграл
     предсказание и оставил его: это находка. Присылать вместе с цифрами
     ping: forced > 0 при 20 мс — дефект, при 200 мс — арифметика
     (HOLE_PATIENCE_MS равен 3 с, но PEER_PREDICT — четыре тика, то есть 66 мс
     игры).
  4. rollbacks= и resent= против петли. На петле отправитель откатывается
     около 21 раза и переотправляет примерно сотню из своих 417 кадров
     (89-139 за семь прогонов на незанятом M3 Pro — разброс от планировщика, а
     не от протокола). По настоящему проводу обе цифры обязаны вырасти, и
     насколько — ровно то, ради чего пункт существует.
  5. sim/net worst= против 16.67 мс — то же чтение, что в пункте M, и здесь
     оно стоит отдельно: сетевая строка мерит сокет, который наконец несёт
     настоящие датаграммы, а не петлевые.

  Подробности и что именно недостаёт второй половине — §14
  docs/owner-verification.md.

--- O. Пакет движка едет на другую машину (спека #20, гейты 1 и 3) --------

  С одной машины собираются все три пакета: macOS хостом, Linux в контейнере
  здесь же, Windows — задачей CI, из которой скрипт забирает артефакт.

  На macOS:

      bash scripts/release.sh --version v0.1.0

  То же самое пишется как --only host: без флага скрипт и так пакует пакет
  своей ОС, а host назван явно, чтобы отказ на чужой ОС нельзя было получить
  опечаткой.

  Ожидаемый вывод — таблица (заголовки латиницей: printf считает ширину
  колонки в байтах, и кириллица их сдвигает), а после повторного прогона той
  же команды — те же цифры до последнего знака:

      release: like-nes-engine-v0.1.0-macos-arm64

      package                                             size  files  sha256
      like-nes-engine-v0.1.0-macos-arm64.tar.gz        <байты>     11  <64 шестнадцатеричных>
      like-nes-engine-v0.1.0-macos-arm64.dmg           <байты>     12  <64 шестнадцатеричных>

      внутри: like-nes/bin/assetc like-nes/bin/editor_shell
              like-nes/bin/libwgpu_native.dylib like-nes/licenses/... version.txt
      манифест: release/v0.1.0/like-nes-engine-v0.1.0-macos-arm64.manifest
      суммы:    release/v0.1.0/SHA256SUMS
      манифест образа: release/v0.1.0/like-nes-engine-v0.1.0-macos-arm64.dmg.manifest
      сумма И РАЗМЕР .dmg от прогона к прогону разные (hdiutil пишет в UDIF
      время и UUID);
      воспроизводится СОДЕРЖИМОЕ образа — его сверяет scripts/check_release_dmg.sh

  Строка .dmg — единственная в таблице, которая МЕНЯЕТСЯ между прогонами, и
  это не находка: формат UDIF несёт время и UUID сборки. Утверждение о
  воспроизводимости здесь про содержимое образа (имена, права, суммы файлов),
  и его проверяет отдельный гейт — сравнивать глазами две строки .dmg не надо.
  У образа на один файл больше, чем у архива: Info.plist бандла.

  Размер числом здесь не записан намеренно: он зависит от тулчейна, которым
  собран пакет, и записанная однажды цифра устарела бы первым же обновлением
  Xcode, превратив пункт в вечно красный. Утверждение — равенство ДВУХ
  прогонов между собой, а не совпадение с бумагой.

  Пакет, его .manifest и SHA256SUMS лежат в release/v0.1.0/. Тега на HEAD
  нет — версию назвать флагом обязательно: без неё скрипт отказывается,
  а не подставляет 0.0.0.

  Дальше — то, чего не проверит ни один раннер. Скопировать архив на машину
  (или в чистую учётку) БЕЗ этого репозитория и без тулчейна:

      tar -xzf like-nes-engine-v0.1.0-macos-arm64.tar.gz
      cat like-nes/version.txt
      ./like-nes/bin/assetc --synthetic /tmp/probe.bundle
      ./like-nes/bin/editor_shell

  1. version.txt называет версию, коммит и тройку — три строки, без unknown.
  2. assetc печатает строку выпечки. Вместо неё ошибка загрузчика
     "Library not loaded: ...libwgpu_native.dylib" — это находка: рантайм
     едет РЯДОМ с бинарями и ищется через @executable_path, и его пропажа
     здесь значит, что пакет не самодостаточен.
  3. editor_shell открывает окно на машине без дерева сборки.
  4. В like-nes/licenses/ семь файлов, ни один не пуст (регресс спеки #9).

  Всё, кроме пункта 3, утверждает и bash scripts/check_release.sh: он
  упаковывает пакет ДВАЖДЫ из одной сборки (свой каталог build-release) и
  сверяет состав поимённо, штамп, нормализацию архива и суммы. Спросить,
  работает ли это на ЧУЖОЙ машине, он не может.

  --- Образ .dmg: то, чем пакет ставят люди ---

  Архив — способ доставки для тех, кто и так живёт в терминале. Обычная
  установка на macOS выглядит иначе, и её тоже надо проверить руками:

      open release/v0.1.0/like-nes-engine-v0.1.0-macos-arm64.dmg

  5. Открывается окно тома с like-nes.app и ярлыком Applications рядом.
  6. Перетащить like-nes.app на Applications, размонтировать том, запустить
     /Applications/like-nes.app двойным щелчком из Finder.
  7. Окно редактора открывается. Ошибка "Library not loaded" здесь значит то
     же, что и в пункте 2, но с добавкой: dylib обязан лежать РЯДОМ с
     исполняемым, в Contents/MacOS, потому что rpath у нас @executable_path.
  8. Gatekeeper на неподписанном бандле скажет "не удаётся проверить
     разработчика" — это ОЖИДАЕМО, подписи и нотаризации в этом раунде нет.
     Открыть через контекстное меню → «Открыть». Отдельный пункт, потому что
     без него шаг 6 читается как отказ пакета.

  Пункты 5-8 не проверяет никто, кроме владельца: раннеру нечем щёлкнуть.
  Всё остальное про образ утверждает bash scripts/check_release_dmg.sh —
  состав бандла поимённо, содержимое (совпало со стейджем), права (в
  Contents/MacOS исполняемо, в Contents/Resources — нет), симлинк на
  /Applications, Info.plist (точка входа, версия, коммит), лицензии, штамп,
  и совпадение содержимого ДВУХ прогонов. На Linux и Windows он пропускается
  вслух: hdiutil есть только на macOS.

  --- Пакет Linux с той же машины ---

      release: контейнер docker, платформа linux/arm64,
               образ like-nes-release:33ceb71981b6-aarch64
      release: база ubuntu@sha256:33ceb719...517

  Первая сборка тянет базовый образ и компилирует всё с нуля — это десятки

  и пакет, собранный «той же командой», перестал бы быть тем же пакетом.

  Дальше — то, чего не проверит ни macOS, ни раннер. Скопировать архив на
  машину с Linux БЕЗ этого репозитория и без тулчейна:

      tar -xzf like-nes-engine-v0.1.0-linux-aarch64.tar.gz

  2. assetc печатает строку выпечки. Ошибка загрузчика про
     libwgpu_native.so — находка: рантайм едет рядом с бинарями и ищется
     через $ORIGIN, и его пропажа значит, что пакет не самодостаточен.
  3. editor_shell открывает окно. Здесь же всплывают X11/Wayland-зависимости

  4. В like-nes/licenses/ семь файлов, ни один не пуст (регресс спеки #9).

  Всё, кроме пунктов 2-3 на ЧУЖОЙ машине, утверждает

  архива и суммы между прогонами. Без --live тот же гейт проверяет одни
  правила (пин базы, монтирование только для чтения, коды отказов) и демона
  не требует — в этом виде он идёт в scripts/preflight.sh.

  --- Пакет Windows из CI ---

  Нужен gh, авторизованный на этом репозитории. Нет клиента или нет входа —
  скрипт отказывается кодом 4 и печатает, ЧТО именно сделать (brew install gh
  либо gh auth login): это разные действия, и одним сообщением на оба
  пришлось бы переустанавливать работающий клиент.

      bash scripts/release.sh --version v0.1.0 --only windows

  Ожидаемый вывод построчно (тег v0.1.0 обязан быть запушен — прогон ищется
  по коммиту, на который тег указывает):

      release: жду прогон release_engine.yml на коммите <12 hex>
               (артефакт like-nes-engine-windows)
      release: прогон <id> зелёный (опросов <N>)
      release-check: OK   архив доехал целым (сумма совпала с SHA256SUMS...)
      release-check: OK   цепочка сошлась: прогон на <коммит>, тот же коммит
                          в штампе, версия v0.1.0
      release-check: OK   состав пакета поимённо (11 файлов)
      release-check: OK   лицензии на месте и непусты (7)
      release-check: OK   штамп называет версию, коммит и тройку
                          (windows-x86_64)
      release: пакет Windows приехал: release/v0.1.0/like-nes-engine-...tar.gz

  Три последние строки — про СОСТАВ, и появились они после того, как гейт
  сверял одну цепочку: пакет без editor_shell.exe, без wgpu_native.dll или с
  лицензией в нуль байт сходился по версии и коммиту и доезжал как успех.
  Сам прогон о пакете не утверждает ничего: там только release.sh и upload.

  Тега на HEAD нет, а проверить путь надо — прогон запускается вручную:

      bash scripts/release_ci.sh --dispatch --version v0.1.0-check

  Ручной запуск работает только тогда, когда release_engine.yml УЖЕ доехал в
  main: workflow_dispatch GitHub берёт из ДЕФОЛТНОЙ ветки, а не из той, что
  указана запуском. Пока файл живёт только в dev, gh отвечает "could not find
  any workflows named release_engine.yml" — это про ветку, а не про машину.
  Сверка с remote стоит раньше: локальный коммит, не запушенный в свою ветку,
  отбивается словами "прогон собрал бы не то дерево".

  Внутри прогона работает ТОТ ЖЕ release.sh: CI даёт Windows-хост, а не
  второй упаковщик. Утверждение про цепочку — главное здесь: прогон обязан
  быть на нашем коммите, артефакт — из этого прогона, а штамп внутри пакета
  обязан называть тот же коммит. Сходятся все три — приехал ТОТ пакет.

  Красный прогон — это отказ со ссылкой (gh run view <id> --log-failed), а не
  зависание: «идёт», «упал» и «зелёный» разведены, и красный не ждёт дедлайна.

  Дальше — то, чего не проверит ни macOS, ни раннер. Скопировать архив на
  машину с Windows БЕЗ этого репозитория и без MSVC:

      tar -xzf like-nes-engine-v0.1.0-windows-x86_64.tar.gz
      type like-nes\version.txt
      like-nes\bin\assetc.exe --synthetic %TEMP%\probe.bundle
      like-nes\bin\editor_shell.exe

  1. version.txt называет версию, коммит и тройку windows-x86_64.
  2. assetc печатает строку выпечки. Ошибка про отсутствующую DLL — находка:
     рантайм wgpu едет рядом с бинарями.
  3. editor_shell открывает окно. Требование Visual C++ Redistributable, если
     оно всплывёт, — это гейт 5 спеки #20.
  4. В like-nes\licenses\ семь файлов, ни один не пуст (регресс спеки #9).

  Правила пути (что собирает прогон, что он НЕ публикует, как выбирается
  прогон) утверждает bash scripts/check_release_ci.sh — он в preflight.sh и
  сети не требует. Живой прогон целиком — bash scripts/check_release_ci.sh
  --live, он занимает раннер до часа.

6. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
===========================================================================

--- "The C compiler ... is not able to compile a simple test program" -----

Смотреть НЕ на первую строку, а на конец вывода. Если там

    --mt=CMAKE_MT-NOTFOUND
    RC Pass 1: command "rc /fo ..." failed ... no such file or directory

то компилятор ни при чём: rc.exe и mt.exe приносит Windows SDK, отдельный
компонент. Лечение:

  1. Visual Studio Installer → Modify → Individual components →
     отметить "Windows 11 SDK" → Modify.
  2. Удалить каталог сборки целиком (out\build\x64-Debug или build):
     в нём застрял кеш с CMAKE_MT-NOTFOUND, он переживёт установку SDK.
  3. В x64 Native Tools Command Prompt проверить: where rc и where mt
     должны печатать пути внутри C:\Program Files (x86)\Windows Kits\10\bin\
  4. Конфигурировать заново.

Строка "windows sdk :" в паспорте owner_check.sh показывает это же —
но она видна только после того, как сборка уже прошла, поэтому проверка
через where быстрее.

--- "like-nes собирается только под 64 бита" -----------------------------

Шелл 32-битный — доустанавливать в VS Installer нечего, x64-компилятор
уже лежит рядом (bin\Hostx64\x64\cl.exe). Самое короткое лечение:

    scripts\win-dev.bat clean
    scripts\win-dev.bat build

Дальше — то же самое руками. "Developer Command Prompt for VS" и "Developer PowerShell"
дают по умолчанию x86-тулчейн (в путях видно bin\Hostx86\x86\cl.exe), а
предсобранный wgpu-native всё равно подставляет x86_64-библиотеку. Лечение:
закрыть шелл, открыть "x64 Native Tools Command Prompt for VS", удалить
каталог build (кеш помнит компилятор) и сконфигурировать заново.

Если гейта не было и сборка дошла до кода — она падает по-другому:
capture.cpp даёт "C4244: преобразование uint64_t в size_t" под /W4 /WX.
Причина та же, наш код тут ни при чём.

--- "cl.exe not found" / CMake берёт не тот компилятор -------------------

Шелл запущен не из x64 Native Tools Command Prompt for VS. Обычный cmd,
PowerShell и Git Bash окружения vcvars не имеют.

--- Игра не находит ассеты -----------------------------------------------

  LIKENES_ASSETS=<путь к example_ugly_game/assets>
  (Windows: set LIKENES_ASSETS=...)

--- "fatal error: GL/gl.h: No such file or directory" (Fedora/Nobara) -----

Падает не наш код, а зависимость glfw3webgpu: заголовок тянет сам glfw3.h
под X11. На Debian он приезжает внутри xorg-dev, у Fedora метапакета нет.

  sudo dnf install -y mesa-libGL-devel

Переконфигурировать не нужно — повторить cmake --build build.

--- "Could not resolve host: github.com" при первом конфигурировании ------

Это DNS, а не дерево: первое конфигурирование качает зависимости. Часто
случается сразу после обновления системы, которое перезапустило резолвер.

  getent hosts github.com        должен напечатать IP
  resolvectl status | head -20   пусто → sudo systemctl restart systemd-resolved

Затем убрать stamp провалившейся загрузки и повторить конфигурирование
(каталог build целиком сносить не надо, скачанное останется):

  rm -rf build/_deps/<имя>-subbuild build/_deps/<имя>-src

--- Пад не виден на Linux ------------------------------------------------

  sudo usermod -aG input $USER   и перелогиниться.

Ещё вероятнее на игровом дистрибутиве: запущенный Steam со Steam Input
подменяет реальный пад виртуальным Xbox 360. На время гейта закрыть Steam.

--- Нет звука на Linux ---------------------------------------------------

Игра скажет "audio: off" и поедет дальше. Нужен pipewire/pipewire-pulse
(раздел 1). Проверить: pactl info
